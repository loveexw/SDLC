## 1. Введение {#1-introduction}

### 1.1 Назначение документа {#11-document-purpose}
Документ определяет, **что** должна делать система SecureBooking: бизнес-цели заказчика, функции, ограничения и требования к качеству, прежде всего к защите персональных данных. Документ предназначен для заказчика (проверка полноты требований), разработчика (основа для проектирования и реализации) и преподавателя (контроль выполнения курсового проекта по ЖЦРПО). Решения о том, **как** будет устроена система, описаны в [`sdd.md`](sdd.md) и записях ADR в папке [`adr/`](adr/); план реализации — в [`plan.md`](plan.md).

### 1.2 Область применения продукта {#12-product-scope}
**SecureBooking 1.0** — настольное приложение для Windows, через которое сотрудники организации бронируют переговорные комнаты. Система показывает расписание переговорной на выбранную дату, не допускает пересечения бронирований и позволяет администратору управлять перечнем комнат. Её отличие от обычного журнала бронирования — защита персональных данных: ФИО, телефон и e-mail сотрудников хранятся только в зашифрованном виде, а доступ к ним разграничен по ролям.

**Бизнес-цели заказчика:**

| ID | Бизнес-требование | Показатель достижения |
|----|-------------------|-----------------------|
| BR-01 | Исключить двойные бронирования одной переговорной | 0 пересекающихся бронирований |
| BR-02 | Персональные данные сотрудников не должны раскрываться при утечке или копировании файлов системы | В файлах на диске нет ФИО, телефонов и e-mail в открытом виде |
| BR-03 | Сотрудник бронирует переговорную сам, без офис-менеджера | Бронирование занимает не более 1 минуты |
| BR-04 | Администратор управляет переговорными и видит контакты организаторов встреч | Все операции администрирования выполняются в приложении |
| BR-05 | Минимальная стоимость внедрения | Нет серверов и платных лицензий; работа на имеющихся ПК с Windows 10/11 |

За рамками версии 1.0: веб- и мобильные клиенты, синхронизация с Outlook и Google Calendar, уведомления, учёт оборудования, оплата.

## 2. Обзор продукта {#2-product-overview}

### 2.1 Перспектива продукта {#21-product-perspective}
SecureBooking — новый самостоятельный продукт. Он заменяет бумажный журнал или общую таблицу, в которых бронирования пересекаются, а телефоны сотрудников доступны всем. Приложение работает локально на ПК с Windows: данные и ключи шифрования хранятся в папке профиля пользователя, внешние сервисы не используются. Шифрование выполняется встроенными средствами Windows.

### 2.3 Ограничения продукта {#23-product-constraints}
- Платформа: Windows 10/11 x64, настольное приложение (Desktop).
- Язык разработки: C++17, среда Visual Studio 2026; интерфейс на WinAPI.
- Без сторонних платных библиотек и серверной части (BR-05).
- Обработка ПД должна соответствовать Закону РБ № 99-З: минимальный состав данных, ограниченный доступ, защита при хранении.
- Язык интерфейса — русский.

### 2.4 Характеристики пользователей {#24-user-characteristics}

| Роль | Описание | Права |
|------|----------|-------|
| Сотрудник | Работник офиса, пользуется приложением несколько раз в неделю, базовые навыки работы с ПК | Бронирование и отмена своих бронирований, свои ПД |
| Администратор | Офис-менеджер или системный администратор | Всё, что может сотрудник, а также переговорные, список пользователей с ПД, аудит хранилища |
| Заказчик | Руководство организации | Не работает с системой напрямую; заинтересован в BR-01…BR-05 |

### 2.5 Допущения и зависимости {#25-assumptions-and-dependencies}
- Учётные записи Windows на рабочих местах защищены паролем: от этого зависит защита ключей шифрования.
- Количество переговорных — до 50, пользователей — до 500, бронирований — до 10 000 в год.
- Рабочее время офиса — с 08:00 до 20:00 (если заказчик изменит его, изменятся REQ-FUNC-005 и прототип GUI).
- Резервное копирование папки профиля выполняется ИТ-службой заказчика.

## 3. Требования {#3-requirements}

Формат идентификатора: `REQ-[AREA]-[NNN]`. Приоритеты: Must — обязательно, Should — желательно, Could — при наличии времени.

### 3.1 Внешние интерфейсы {#31-external-interfaces}

#### 3.1.1 Пользовательские интерфейсы {#311-user-interfaces}

- **ID:** REQ-INT-001
- **Title:** Оконный интерфейс
- **Statement:** Система должна предоставлять оконный интерфейс из окон: вход, регистрация, главное окно с расписанием, «Мои бронирования», профиль, а для администратора — «Переговорные», «Пользователи», «Хранилище».
- **Rationale:** BR-03 — бронирование без обучения и без офис-менеджера.
- **Acceptance Criteria:** все окна соответствуют прототипам из раздела 5; все действия UC-01…UC-10 доступны из интерфейса.
- **Verification Method:** Demonstration
- **More Information:** прототипы — [`sysml/Mockups.sysml`](sysml/Mockups.sysml), `images/mockup-*.png`. Приоритет: Must.

- **ID:** REQ-INT-002
- **Title:** Понятные сообщения об ошибках
- **Statement:** Система должна сообщать об ошибке ввода на русском языке с указанием, что именно исправить.
- **Rationale:** снижает количество обращений к администратору.
- **Acceptance Criteria:** для каждого правила проверки из 3.2 существует отдельное сообщение (например, «Телефон должен быть в формате +375XXXXXXXXX»).
- **Verification Method:** Test
- **More Information:** Приоритет: Must.

#### 3.1.2 Аппаратные интерфейсы {#312-hardware-interfaces}
Не требуются: система работает на стандартном ПК.

#### 3.1.3 Программные интерфейсы {#313-software-interfaces}

- **ID:** REQ-INT-003
- **Title:** Криптография средствами ОС
- **Statement:** Система должна выполнять шифрование и хеширование встроенными криптографическими средствами Windows.
- **Rationale:** BR-05 — без сторонних библиотек; проверенные реализации алгоритмов.
- **Acceptance Criteria:** в составе поставки нет сторонних криптографических библиотек.
- **Verification Method:** Inspection
- **More Information:** Приоритет: Should.

### 3.2 Функциональные требования {#32-functional}

- **ID:** REQ-FUNC-001
- **Title:** Регистрация пользователя
- **Statement:** Система должна регистрировать пользователя по логину, паролю, ФИО, телефону и e-mail.
- **Rationale:** BR-03; ПД нужны, чтобы связаться с организатором встречи.
- **Acceptance Criteria:** логин — 3–20 символов (латиница, цифры, `_`, `.`), уникален без учёта регистра; пароль — не менее 8 символов, содержит буквы и цифры, вводится дважды; ФИО — не менее двух слов, без цифр; телефон — `+375XXXXXXXXX` или `80XXXXXXXXX`; e-mail — корректный адрес, уникален.
- **Verification Method:** Test
- **More Information:** UC-01, `mockup-02-registration.png`. Приоритет: Must.

- **ID:** REQ-FUNC-002
- **Title:** Первый администратор
- **Statement:** Система должна назначать роль администратора первому зарегистрированному пользователю.
- **Rationale:** при первом запуске в системе ещё нет администратора, который мог бы выдать права.
- **Acceptance Criteria:** при пустой базе форма регистрации называется «Создание администратора», созданный пользователь имеет роль «Администратор»; следующие пользователи получают роль «Сотрудник».
- **Verification Method:** Test
- **More Information:** Приоритет: Must.

- **ID:** REQ-FUNC-003
- **Title:** Вход в систему
- **Statement:** Система должна допускать к работе только пользователя, указавшего верные логин и пароль.
- **Rationale:** BR-02 — разграничение доступа к ПД.
- **Acceptance Criteria:** при неверных логине или пароле выводится одно и то же сообщение «Неверный логин или пароль».
- **Verification Method:** Test
- **More Information:** UC-02, `mockup-01-login.png`. Приоритет: Must.

- **ID:** REQ-FUNC-004
- **Title:** Расписание переговорной
- **Statement:** Система должна показывать занятые и свободные интервалы выбранной переговорной на выбранную дату с указанием организатора и цели встречи.
- **Rationale:** BR-03 — сотрудник сразу видит, когда переговорная свободна.
- **Acceptance Criteria:** интервалы упорядочены по времени, свободные отмечены «свободно»; выбор свободного интервала подставляет время в форму бронирования.
- **Verification Method:** Demonstration
- **More Information:** UC-03, `mockup-03-main.png`. Приоритет: Must.

- **ID:** REQ-FUNC-005
- **Title:** Правила бронирования
- **Statement:** Система должна принимать бронирование только с 08:00 до 20:00, с шагом 30 минут, длительностью не более 4 часов, не ранее текущего момента и не позднее чем через 30 дней, с указанной целью встречи.
- **Rationale:** BR-01, BR-03 — правила офиса; справедливое распределение переговорных.
- **Acceptance Criteria:** бронирование, нарушающее любое правило, отклоняется с сообщением о причине.
- **Verification Method:** Test
- **More Information:** UC-04. Приоритет: Must.

- **ID:** REQ-FUNC-006
- **Title:** Запрет пересечений
- **Statement:** Система не должна допускать пересечения интервалов бронирований одной переговорной в одну дату.
- **Rationale:** BR-01.
- **Acceptance Criteria:** при занятом 10:00–12:00 отклоняются 11:00–12:30, 09:30–10:30 и 10:00–12:00; допускается 12:00–13:00 (стык).
- **Verification Method:** Test
- **More Information:** UC-04. Приоритет: Must.

- **ID:** REQ-FUNC-007
- **Title:** Отмена бронирования
- **Statement:** Система должна позволять сотруднику отменять только свои бронирования, а администратору — любые.
- **Rationale:** BR-04; защита от случайной отмены чужих встреч.
- **Acceptance Criteria:** попытка отменить чужое бронирование сотрудником отклоняется; перед отменой запрашивается подтверждение.
- **Verification Method:** Test
- **More Information:** UC-05, UC-06, `mockup-04-my-bookings.png`. Приоритет: Must.

- **ID:** REQ-FUNC-008
- **Title:** Управление переговорными
- **Statement:** Система должна позволять администратору добавлять переговорные (название, вместимость, этаж, оборудование) и удалять их вместе с бронированиями.
- **Rationale:** BR-04.
- **Acceptance Criteria:** название уникально; вместимость — 1…500; удаление требует подтверждения; у сотрудника нет доступа к функции.
- **Verification Method:** Test
- **More Information:** UC-08, `mockup-05-rooms.png`. Приоритет: Must.

- **ID:** REQ-FUNC-009
- **Title:** Изменение своих данных
- **Statement:** Система должна позволять пользователю изменить свои ФИО, телефон, e-mail и пароль.
- **Rationale:** данные сотрудников меняются; право субъекта ПД на их актуализацию (Закон № 99-З).
- **Acceptance Criteria:** смена пароля требует ввода текущего пароля; к новым данным применяются правила REQ-FUNC-001.
- **Verification Method:** Test
- **More Information:** UC-07. Приоритет: Must.

- **ID:** REQ-FUNC-010
- **Title:** Просмотр пользователей и хранилища
- **Statement:** Система должна позволять администратору просматривать список пользователей с расшифрованными ПД и содержимое файла хранилища.
- **Rationale:** BR-04; администратор может убедиться, что ПД на диске зашифрованы (BR-02).
- **Acceptance Criteria:** окно «Хранилище» показывает файл как есть: ФИО, телефоны и e-mail видны только в виде шифртекста.
- **Verification Method:** Demonstration
- **More Information:** UC-09, UC-10, `mockup-06-users.png`, `mockup-07-storage.png`. Приоритет: Could. **Перенесено в версию 1.1** по решению заказчика от 19.11.2026.

- **ID:** REQ-FUNC-011
- **Title:** Повторяющиеся бронирования
- **Statement:** Система должна позволять создать еженедельную серию бронирований переговорной (день недели, время, период действия) и отменить серию целиком или одну дату.
- **Rationale:** BR-03; еженедельные планёрки не должны бронироваться вручную каждый раз (заказчик, 19.11.2026).
- **Acceptance Criteria:** серия создаётся, только если все её даты удовлетворяют REQ-FUNC-005 и REQ-FUNC-006; при конфликте выводится список занятых дат; отмена серии удаляет все её будущие брони.
- **Verification Method:** Test
- **More Information:** SDD: SYS-15, функция F12. Приоритет: Must.

- **ID:** REQ-FUNC-012
- **Title:** Экспорт и печать расписания
- **Statement:** Система должна выгружать расписание переговорной за выбранный период в файл CSV и выводить его на печать.
- **Rationale:** офис-менеджер вывешивает расписание на дверь переговорной, бухгалтерии нужен файл для Excel (заказчик, 19.11.2026).
- **Acceptance Criteria:** файл CSV открывается в Excel без искажения кириллицы; в выгрузке и на печати чужие телефоны маскируются (REQ-SEC-007).
- **Verification Method:** Test, Demonstration
- **More Information:** SDD: SYS-16, функция F13. Приоритет: Should.

### 3.3 Качество обслуживания {#33-quality-of-service}

#### 3.3.1 Производительность {#331-performance}

- **ID:** REQ-PERF-001
- **Title:** Скорость отображения
- **Statement:** Система должна отображать расписание переговорной не дольше 0,5 с при 10 000 бронирований в базе.
- **Rationale:** BR-03 — бронирование за 1 минуту.
- **Acceptance Criteria:** замер на ПК с процессором уровня Core i3 и 8 ГБ ОЗУ.
- **Verification Method:** Test
- **More Information:** Приоритет: Should.

#### 3.3.2 Безопасность {#332-security}

- **ID:** REQ-SEC-001
- **Title:** Шифрование персональных данных
- **Statement:** Система должна хранить ФИО, телефон и e-mail на диске только в зашифрованном виде (AES-256-GCM, уникальный случайный вектор инициализации для каждого значения).
- **Rationale:** BR-02.
- **Acceptance Criteria:** поиск ФИО, телефона или e-mail любого пользователя в файлах данных не находит совпадений; одинаковые значения дают разный шифртекст.
- **Verification Method:** Test, Inspection
- **More Information:** Приоритет: Must.

- **ID:** REQ-SEC-002
- **Title:** Контроль целостности
- **Statement:** Система должна обнаруживать изменение данных вне программы и отказываться работать с изменёнными данными.
- **Rationale:** BR-02; защита от подмены записей.
- **Acceptance Criteria:** изменение любого байта файла данных приводит к сообщению «Нарушена целостность файла базы».
- **Verification Method:** Test
- **More Information:** Приоритет: Must.

- **ID:** REQ-SEC-003
- **Title:** Хранение паролей
- **Statement:** Система должна хранить пароли только в виде хеша PBKDF2-HMAC-SHA256 с индивидуальной солью (не менее 100 000 итераций).
- **Rationale:** BR-02; при утечке файла пароли не восстанавливаются.
- **Acceptance Criteria:** пароль в открытом виде отсутствует в файлах; у одинаковых паролей разные хеши.
- **Verification Method:** Test, Inspection
- **More Information:** Приоритет: Must.

- **ID:** REQ-SEC-004
- **Title:** Защита ключей
- **Statement:** Система должна хранить ключи шифрования отдельно от данных и защищёнными средствами ОС (DPAPI).
- **Rationale:** ключ, лежащий рядом с данными в открытом виде, делает шифрование бесполезным.
- **Acceptance Criteria:** копия файлов, перенесённая на другой компьютер или в другую учётную запись, не расшифровывается.
- **Verification Method:** Test
- **More Information:** Приоритет: Must.

- **ID:** REQ-SEC-005
- **Title:** Защита от перебора паролей
- **Statement:** Система должна блокировать вход по логину на 60 с после 5 неудачных попыток подряд.
- **Rationale:** BR-02.
- **Acceptance Criteria:** шестая попытка в течение 60 с отклоняется даже с верным паролем.
- **Verification Method:** Test
- **More Information:** Приоритет: Should.

- **ID:** REQ-SEC-006
- **Title:** Уникальность e-mail без расшифровки
- **Statement:** Система должна проверять уникальность e-mail без расшифровки ПД других пользователей.
- **Rationale:** принцип минимального доступа к ПД.
- **Acceptance Criteria:** регистрация с e-mail, отличающимся только регистром, отклоняется.
- **Verification Method:** Test
- **More Information:** Приоритет: Should.

- **ID:** REQ-SEC-007
- **Title:** Ограничение видимости чужих ПД
- **Statement:** Система должна показывать сотруднику ФИО других сотрудников в виде «Фамилия И. О.», а их телефоны — маскированными; полные данные видит только сам владелец и администратор.
- **Rationale:** BR-02, Закон № 99-З — доступ к ПД только по необходимости.
- **Acceptance Criteria:** в расписании сотрудника чужой телефон отображается как `+375 ** ***-**-67`.
- **Verification Method:** Demonstration
- **More Information:** `mockup-03-main.png`. Приоритет: Must.

#### 3.3.3 Надёжность {#333-reliability}

- **ID:** REQ-REL-001
- **Title:** Сохранность данных при сбое
- **Statement:** Система должна сохранять данные так, чтобы сбой во время записи не повреждал ранее сохранённые данные.
- **Rationale:** потеря базы бронирований останавливает работу офиса.
- **Acceptance Criteria:** при принудительном завершении процесса во время сохранения база открывается в последнем согласованном состоянии.
- **Verification Method:** Test
- **More Information:** Приоритет: Should.

Отдельные требования не предъявляются: приложение локальное и доступно, пока работает ПК.

### 5.2 Вопросы, вынесенные на согласование с заказчиком
1. Рабочее время офиса и шаг бронирования (сейчас 08:00–20:00, 30 минут).
2. Максимальная длительность бронирования (сейчас 4 часа) и горизонт (30 дней).
3. Нужна ли регистрация «самостоятельно» или учётные записи создаёт только администратор.
4. Нужны ли повторяющиеся бронирования (еженедельные планёрки) — в версии 1.0 не предусмотрены.
