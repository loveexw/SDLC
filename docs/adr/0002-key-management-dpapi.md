# Управление ключами: раздельные ключи, защита DPAPI, слепой индекс

## Контекст и постановка задачи
Шифрование бесполезно, если ключ лежит рядом с данными в открытом виде. Нужно решить, где хранить ключ и как проверять уникальность e-mail, не расшифровывая всю базу.

## Драйверы решения
- ключ не должен храниться в открытом виде;
- пользователю не нужно вводить отдельный мастер-пароль;
- поиск совпадений e-mail без расшифровки;
- принцип «один ключ — одна цель».

## Рассмотренные варианты
- случайные ключи, защищённые DPAPI;
- ключ, выводимый из мастер-пароля администратора (PBKDF2);
- ключ, «зашитый» в программу.

## Итог решения
При первом запуске генерируются три случайных 256-битных ключа: `Kenc` (AES-GCM), `Kidx` (HMAC для индекса e-mail), `Kmac` (HMAC файла базы). Они хранятся в файле `master.key`, защищённом **DPAPI** с привязкой к учётной записи Windows и дополнительной энтропией приложения.

Уникальность e-mail проверяется по **слепому индексу** `HMAC-SHA256(Kidx, нормализованный e-mail)`.

### Последствия
- Хорошо: копия файлов, унесённая на другой компьютер или в другую учётную запись, не расшифровывается.
- Хорошо: мастер-пароль не нужен, ключи не попадают в исходный код.
- Плохо: при переустановке Windows без резервной копии профиля данные будут потеряны. В промышленной версии нужен экспорт ключей.
- Нейтрально: слепой индекс раскрывает только факт совпадения e-mail, но не сам адрес.

### Подтверждение
Тесты «DPAPI: защита и восстановление ключа» и «Регистрация: повторный логин и e-mail отклоняются».

## Плюсы и минусы вариантов
### DPAPI
- Хорошо: защита средствами ОС, прозрачно для пользователя.
- Плохо: привязка к учётной записи.
### Мастер-пароль
- Хорошо: переносимость.
- Плохо: пароль нужно вводить при каждом запуске; если его забыть, данные потеряны.
### Ключ в программе
- Плохо: извлекается дизассемблированием, по сути — отсутствие защиты.

## Дополнительная информация
Требования SRS: REQ-SEC-004, REQ-SEC-006. Системные требования: SYS-02, SYS-04. Функции: F01, F02.
